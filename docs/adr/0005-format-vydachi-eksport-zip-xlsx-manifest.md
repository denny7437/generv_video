# 0005. Формат выдачи готового ролика: пакетный экспорт ZIP + XLSX-манифест

**Статус:** предложено · **Дата:** 2026-08-18 · **Задача:** TEC-48 · **Утвердил:** —

## Контекст

Стадия [7] Публикация (записка §5.1, владелец A-31) замыкает сквозной путь «заказ → … → выдача».
API-загрузка видео официально не документирована ни у Ozon, ни у WB (записка §5.1, риск §8) —
поэтому основной путь MVP — экспорт файлов, спроектированный под **400 SKU за раз**, а не под
одиночную выгрузку. Обещание продукта «закрой видео 400 карточек за ночь» (клин № 2, §2.3)
выполняется именно здесь: селлер получает пакет, а не список ссылок.

Контракта выдачи не существует: TEC-13 был Canceled, эндпоинта в `contracts/openapi/api.yaml` нет,
очереди `publish` нет. Эта задача (TEC-48) фиксирует контракт до кода: OpenAPI-эндпоинт,
схему job и формат ZIP+XLS.

Вопрос, который нельзя обойти молча: **что именно получает селлер и в каком формате** — это
определяет и эндпоинт, и очередь, и выбор библиотек. Требование «манифест SKU → файл ролика →
статус» задано в acceptance задачи и в риске §8 («батч-шаблон XLS, инструкция, оценка времени
селлера»).

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Лицензия/стоимость |
|---|---|---|---|
| **(а) Пакетный экспорт ZIP + XLSX-манифест** | закрывает «400 карточек за ночь» без API; манифест — готовый батч-шаблон для ручной загрузки; отклонённые SKU попадают в отчёт покрытия тем же файлом; один скачиваемый артефакт | селлер заливает файлы на площадку вручную — обещание выполняется «наполовину» (риск §8); нужна инструкция в архиве | MIT-библиотеки, 0 ₽ лицензионных |
| **(б) API-публикация в карточку** | полная автоматизация, селлер не касается файлов | API по видео не документирован ни у одной площадки; требует исследования и переговоров; записка §5.4 выносит за MVP | вне MVP |
| **(в) Presigned-ссылки на отдельные файлы** | минимальная реализация | 400 ссылок неудобно и не решает пакет; нет батч-манифеста и статусов; не масштабируется на сотни SKU | — |

## Решение

**Вариант (а) — пакетный экспорт ZIP + XLSX-манифест как единственный путь выдачи MVP.**
Вариант (б) фиксируется как целевой для фазы 3 и не реализуется сейчас; интерфейс очереди
`publish` остаётся единственной точкой публикации, чтобы фаза 3 добавляла API-загрузку, не меняя
контракт выдачи.

### Формат ZIP (спека)

```
<export_id>.zip
  videos/
    <sku>.mp4          # готовый дериват по preset_id; имя файла = артикул селлера
  manifest.xlsx        # манифест: SKU → файл ролика → статус (до 400 строк)
  README.txt           # инструкция по ручной загрузке на площадку + оценка времени
```

Манифест (XLSX, лист `manifest`), колонки:

| Колонка | Тип | Назначение |
|---|---|---|
| `sku` | string | артикул селлера |
| `marketplace` | enum | ozon / wb |
| `title` | string | название товара |
| `video_file` | string | имя файла в `videos/`, пусто если отклонён |
| `status` | enum | `ready` / `rejected` |
| `reject_reason` | enum | `source_rejected` / `qc_failed` / `max_attempts_reached` (только при rejected) |
| `attempts_used` | integer | число потраченных попыток |

Отклонённый SKU **не исчезает** из манифеста: он попадает туда со статусом `rejected` и причиной —
это и есть отчёт по покрытию (записка §3.4, стадия [2] предупреждение о знаменателе метрики).
`video_file` пустой, `reject_reason` заполнен, `attempts_used` отражает потраченные попытки.

**Числа формата — только ссылками.** Разрешение, fps, кодек, лимит веса для каждого деривата живут
в `configs/master_format.yaml → derivatives[].id`. Контракт и код ссылаются на `preset_id`
(идентификатор деривата), значения в payload и в код не копируются (принцип 4, §7.1). Пакетный
лимит `maxItems: 400` — размерность из записки §5.1 («под 400 SKU за раз»), не настраиваемый
параметр формата.

### Эндпоинт и очередь

- `POST /exports` → `202` + `ExportRef`; `GET /exports/{id}` → статус + `summary` (готово/отклонено)
  + ссылки на архив и манифест (ключи S3, не пути ФС).
- `contracts/queues/publish.json` — job публикации. Это **не платная очередь генерации**:
  `attempt_policy.billable=false` на техническом ретрае (пересборка архива не стоит денег генерации),
  `cost_estimate` покрывает CDN/хранение (`cost_targets.cost.other_compute_breakdown_rub.cdn_and_storage`).

## OSS-разведка (нулевая фаза)

Проверено 2026-08-18. Зависимости появятся в задаче worker-publish (A-31), не в этом контракте —
здесь фиксируется выбор, чтобы реализация не перерешала его в одиночку.

**XLSX-манифест:**

| Кандидат | Лицензия | Активность | Вердикт |
|---|---|---|---|
| `exceljs/exceljs` | MIT | 15,4 тыс. звёзд, 2,0 тыс. форков, активен | **reuse** — чистая MIT, потоковая запись, OpenSSF license 10/10 |
| SheetJS `xlsx` (npm) | Apache-2.0 (CE) | npm-версия заморожена на 0.18.5 (2022) | **отказ** — CVE-2023-30533 (prototype pollution), фиксы только на cdn.sheetjs.com (0.19.3+/0.20.2+), нестандартная установка, вендор-лок |
| `node-xlsx` | MIT | тонкая обёртка | отказ — дублирует exceljs без выигрыша |

**ZIP:**

| Кандидат | Лицензия | Активность | Вердикт |
|---|---|---|---|
| `archiver` | MIT | живой, потоковый (streams) | **reuse** — потоковая сборка, обязательна под сотни файлов/гигабайты |
| `jszip` | MIT | самый популярный | отказ для сервера — сборка в памяти (`generateAsync`), на 400 файлов упирается в RAM |
| `adm-zip` | MIT | 2,2 тыс. звёзд | отказ — in-memory, исторические CVE в 0.5.14–0.5.16 |

Итог: `exceljs` (MIT) для XLSX-манифеста, `archiver` (MIT) для ZIP. Оба — reuse через адаптер
в `services/worker-publish`, чтобы замена библиотеки не касалась домена.

## Последствия

- **Клиентский сценарий закрыт.** Селлер получает один архив с видео, манифестом и инструкцией —
  «400 карточек за ночь» без написания API-интеграции.
- **Покрытие видно в выдаче.** Отклонённые SKU с причиной — в манифесте и в `summary` API-ответа,
  без отдельного отчёта.
- **Деньги защищены.** Повторная доставка экспорта не тарифицируется как генерация; стоимость
  экспорта — только CDN/хранение.
- **Фаза 3 не ломает контракт.** API-загрузка добавляется как реализация за тем же интерфейсом
  очереди `publish`; схема выдачи и эндпоинт не меняются.
- **Проверяемо.** `pnpm check:queues` (обязательный минимум полей) и `pnpm check:openapi` (линтер
  Redocly) зелёные; формат описан здесь, а не в комментарии Linear.
- **Вне скоупа.** Реализация worker-publish, сам экспортный код, API-публикация — отдельные задачи
  A-31/A-32. Строка в `docs/oss-registry.md` и `NOTICE` добавляется в задаче worker-publish вместе
  с зависимостями (иначе `pnpm check:oss` упадёт на отсутствующей dependency).
