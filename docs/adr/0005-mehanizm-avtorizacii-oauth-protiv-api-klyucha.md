# 0005. Механизм авторизации площадок: OAuth 2.0 code flow против статического API-ключа

**Статус:** предложено · **Дата:** 2026-08-18 · **Задача:** TEC-41 · **Решение за:** Денисом Нагаевым

## Контекст

Импорт карточки по ссылке идёт через официальный API площадки (ADR-0003, принят), а значит —
требует авторизации продавца. В схеме уже есть сущность «подключение кабинета»
(`marketplace_connections`: `credential_ref`, `status`), но контракта самой авторизации нет:
как продавец даёт сервису доступ к своему кабинету, и чем различаются площадки.

Ключевой факт нулевой фазы (OSS-разведка, 2026-08-18): **площадки несимметричны по механизму**:

- **Ozon** поддерживает оба пути — OAuth 2.0 Authorization Code flow (RFC 6749, с `state`/CSRF)
  и статические ключи (Client-Id + Api-Key);
- **Wildberries** для контента продавца даёт только статические API-токены (Content/Statistics),
  OAuth-флоу для seller-контента нет.

Отсюда вопрос: делать контракт под один механизм «на все площадки» или признать несимметрию
и спроектировать под неё.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Лицензия/стоимость |
|---|---|---|---|
| **(а) Только OAuth code flow** | единый флоу, короткоживущие токены, отзыв/ротация без рук продавца, нет чужих статических ключей у нас на руках | WB не даёт OAuth для seller-контента — для Wildberries флоу невозможен; запираем WB-импорт | протокол — открытый стандарт (RFC 6749/7636) |
| **(б) Только статический API-ключ** | одинаково работает на обеих площадках; простейший контракт (сегодняшний `POST /connections`) | теряем Ozon OAuth: селлер вручную копирует Client-Id/Api-Key — выше трение входа; у нас на руках долгоживущий чужой ключ; нет ротации без участия продавца | — |
| **(в) Оба механизма за одним адаптером** | покрывает реальность площадок; Ozon получает лучший UX (OAuth), WB работает на ключе; провайдер-специфика за адаптером (правило ADR-0003) | контракт чуть шире: два флоу, поле `auth_method`; адаптер A-31 реализует оба | протокол — стандарт; клиент — `openid-client` (MIT) |

## Решение

**Вариант (в): оба механизма за единым интерфейсом подключения, механизм — поле `auth_method`,
по умолчанию Ozon → `oauth`, Wildberries → `api_key`.** Обоснование:

1. **Несимметрия — факт площадок, а не наш выбор.** Делать «OAuth на всё» нельзя: WB его не даёт.
   Делать «ключ на всё» — отказываемся от лучшего UX там, где OAuth есть (Ozon), и добровольно
   держим долгоживущие чужие ключи, где можно держать короткоживущие токены.
2. **OAuth снижает трение и риск.** Один редирект на Ozon против ручного копирования пары
   Client-Id/Api-Key; токены короткоживущие, ротация/отзыв — штатно (refresh token), а не через
   перевыпуск ключа продавцом.
3. **Провайдер-специфика остаётся за адаптером** (как у провайдеров генерации, ADR-0003):
   домен видит `auth_method` и `credential_ref`, а обмен `code→token`, параметры `client_id`/
   `redirect_uri`/`scopes` и формат `state` живут в адаптере площадки (задача A-31) и в конфиге
   (`configs/platform_specs.yaml`), а не в контракте.
4. **Секреты не в схеме.** В БД — только `credential_ref` (имя ключа секрет-менеджера). Значение
   токена/ключа не попадает ни в БД, ни в контракт, ни в логи; для OAuth обмен токеном идёт
   server-to-server, токены пишутся сразу в секрет-менеджер.

Клиент OAuth — `openid-client` (`panva/node-openid-client`, MIT, сертифицированный OIDC-клиент,
поддержка Authorization Code flow + PKCE). Берётся как зависимость **в задаче A-31**, не в этом
контракте: контракт фиксирует протокол (стандарт OAuth 2.0), а не библиотеку.

## Последствия

- **Схема БД:** `marketplace_connections` дополняется `auth_method` (`oauth` | `api_key`) и
  `expires_at` (срок жизни access-токена, `NULL` для ключа). `status`/`scope` уже есть.
  Миграция forward-only `0003_auth.sql`, откат — DROP COLUMN.
- **Контракт:** единая точка входа `POST /connections/{marketplace}` (площадка переезжает в путь),
  callback `GET /connections/{marketplace}/callback` (без bearer — это редирект из чужого домена,
  безопасность через `state`), статус `GET /connections/{id}` (существующий). Для `oauth` ответ
  200 + `authorizationUrl`/`state`, для `api_key` — 201 + подключение.
- **Безопасность:** `state` обязателен как CSRF-защита; `code` одноразовый; значения токенов в
  ответе callback не возвращаются (только 302-редирект на фронтенд), итог селлер видит опросом
  статуса. Ozon-специфика (PKCE при необходимости, refresh) — в адаптере.
- **Открытые вопросы для A-31:** регистрация OAuth-приложения в Ozon (client_id/secret), URL
  callback, набор scopes для чтения карточек. Значения — в конфиге и секрет-менеджере, не в коде.
