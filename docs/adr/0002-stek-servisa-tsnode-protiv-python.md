# 0002. Стек сервиса: TS/Node для всего, Python — только в ML-воркерах

**Статус:** предложено (требует утверждения человеком) · **Дата:** 2026-08-17 · **Задача:** TEC-33

## Контекст

Сошлись два факта, которые противоречат друг другу, и решать это молча нельзя:

1. **Регламент 04 компании (§2.1)** фиксирует стек разработки — TypeScript/Node. Под него уже собран скелет монорепо (ADR-0001): pnpm workspaces, `tsc --noEmit`, vitest, 51 зелёный тест, дорогая и рискованная логика вынесена в чистые функции без ffmpeg/сети/БД.
2. **Записка §5.3** предлагает для API и бэкенда Python 3.12 + FastAPI с аргументом «вся ML-обвязка на Python, не плодим языки» — и тут же, в той же таблице, указывает фронтенд Next.js (TypeScript). Окончательное решение записка явно оставляет за агентом-архитектором через ADR.

Доменный контекст добавляет ясности: 95 % себестоимости ролика — оплата попыток генерации, а не compute бэкенда (записка §3.1). Бэкенд здесь не вычислительно тяжёлый — это оркестрация, бюджет, доменные типы и чистые функции QC/сборки. Тяжёлые вычисления (сегментация, апскейл, VLM-контроль) записка сама выносит в «отдельный GPU-пул» (§5.1, §5.3). То есть спор о языке касается в основном оркестрационного слоя, а не GPU-вычислений.

## Критерии сравнения

По acceptance задачи TEC-33, каждый вариант оценивается по четырём осям: **цена миграции существующего скелета**, **соответствие регламенту 04**, **найм**, **ML-экосистема**.

## Рассмотренные варианты

### (а) TS/Node для всего, Python — только в ML-воркерах

API, фронтенд, оркестрация, домен, budget-guard, QC-логика и сборка — на TS/Node, на существующем скелете. Python появляется только в GPU-воркерах ML-обвязки: сегментация (SAM-класс), апскейл (Real-ESRGAN-класс), VLM-контроль соответствия. Эти воркеры — отдельный пул, они общаются с остальным контуром через очередь и S3-ключи, а не через общий процесс.

- **Цена миграции:** ~нулевая. Скелет не трогается; Python появляется ровно там, где его ещё нет, и где он обязателен.
- **Регламент 04:** соблюдён — основной стек TS/Node; ML-воркеры в отдельном пуле — обоснованное исключение, зафиксированное этим ADR.
- **Найм:** TS/Node на бэкенд (широкий рынок, совпадает с фронтендом Next.js), Python-инженер — только на ML-обвязку.
- **ML-экосистема:** SAM, Real-ESRGAN, VLM живут в родном Python/PyTorch; граница языка совпадает с границей «GPU-пул», провайдер- и модель-специфика в домен не течёт.

### (б) Python для всего (FastAPI API + Python-воркеры)

Переписать скелет (packages/domain, budget-guard, apps/api, worker-assembly, worker-qc, тесты) на Python 3.12 + FastAPI; оркестрация — Celery/Temporal по записке.

- **Цена миграции:** высокая. Полный перенос 51 теста и чистой логики на другой язык; скелет — уже работающий артефакт, его выбрасывание — потеря, а не выигрыш.
- **Регламент 04:** нарушен — основной стек уходит в Python; потребуется пересмотр регламента человеком, что вне компетенции агента.
- **Найм:** Python-бэкенд шире на рынке, но TS/Node всё равно остаётся для фронтенда Next.js (записка сама это фиксирует), так что «не плодим языки» недостижимо ни в одном варианте.
- **ML-экосистема:** идеальна — всё на одном языке. Но ML — это 3 из 7 стадий, а не весь сервис; остальные 4 стадии на Python не выигрывают.

### (в) TS/Node для всего, включая ML-обвязку

SAM/Real-ESRGAN/VLM исполнять из Node: ONNX Runtime (onnxruntime-node) или подпроцесс/биндинги.

- **Цена миграции:** ~нулевая для скелета, но высокая скрытая — перегон/оборачивание ML-моделей в ONNX; часть моделей (актуальные SAM2/апскейлеры/VLM) существует только в PyTorch, ONNX-порты отстают или отсутствуют.
- **Регламент 04:** формально соблюдён.
- **Найм:** TS-инженеры на ML-инференс — узкий и дорогой рынок.
- **ML-экосистема:** худший вариант — борьба с инструментами вместо работы над продуктом; VLM-инференс из Node через ONNX — тормоз и источник багов.

| Вариант | Цена миграции | Регламент 04 | Найм | ML-экосистема |
|---|---|---|---|---|
| (а) TS/Node + Python только ML-воркеры | ~нулевая | соблюдён | широкий TS + точечный Python | родная для ML, изолирована в GPU-пуле |
| (б) Python всё | высокая (выброс скелета) | нарушен | Python шире, TS всё равно нужен | идеальная, но ML — лишь часть сервиса |
| (в) TS/Node всё | ~нулевая для скелета, скрытая для ML | формально соблюдён | узкий и дорогой | борьба с ONNX вместо продукта |

## Решение

**Рекомендация — вариант (а): TS/Node для всего продукта, Python — только в ML-воркерах GPU-пула.** Обоснование:

1. **Нулевая цена миграции.** Существующий скелет зелёный, тестируемый и построен по регламенту 04 — выбрасывать его ради другого языка нет причины.
2. **Соответствие регламенту 04.** Основной стек остаётся TS/Node; Python локализуется в отдельном пуле как осознанное исключение, зафиксированное этим ADR, а не размазанное по всему коду.
3. **Аргумент записки «не плодим языки» опровергается самой запиской.** Фронтенд Next.js — TypeScript независимо от выбора бэкенда. Один язык для всего недостижим ни в одном варианте; вопрос лишь в том, где провести границу.
4. **Граница языка совпадает с уже зафиксированной границей архитектуры.** Записка §5.1/§5.3 сама выносит тяжёлые вычисления в отдельный GPU-пул. Язык воркера — деталь реализации за контрактом очереди и S3-ключом; она не обязана просачиваться в домен, API или бюджетную логику.

**Правило границы (вшивается в контракт и ревью):** Python-код не покидает GPU-пул. ML-воркеры общаются с остальным контуром только через схемы job в `contracts/queues/` и ключи S3 в `contracts/db/schema.sql`; домен, API, оркестрация, budget-guard, QC-логика и сборка остаются TS/Node. Смена языка реализации воркера за этим контрактом — не ломающее изменение.

## Последствия

**Хорошие.** Скелет и 51 тест сохраняются без изменений; `pnpm verify` продолжает покрывать весь не-ML-контур. Python-воркеры тестируются изолированно (вход — job, выход — артефакт в S3), их внутренности не влияют на доменные контракты. Найм: TS/Node закрывает бэкенд и фронт одной командой, Python-инженер — только ML-обвязка.

**Цена.** В контуре появляются два рантайма — но граница между ними совпадает с границей «дешёвый orchestration / дорогой GPU» и с уже существующей границей модулей (воркеры не ходят в БД мимо домена, провайдер-специфика не покидает render-воркер). Оркестрация длинных задач остаётся на BullMQ (Redis), уже заложенной в скелете и контрактах; выбор между BullMQ и Temporal/Celery из записки §5.3 — отдельный вопрос и отдельный ADR, на язык сервиса он не влияет.

**Проверяемо.** `pnpm check:openapi` и `pnpm verify` зелёные — этот ADR контрактов не меняет. Граница языка контролируется на ревью: Python-файл вне GPU-пула — блокирующее замечание, как и провайдер-специфика вне render-воркера.
