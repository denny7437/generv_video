# 0003. Способ импорта карточки: официальный API площадки против публичной страницы

**Статус:** предложено · **Дата:** 2026-08-18 · **Задача:** TEC-26 · **Решение за:** Денисом Нагаевым

## Контекст

Решение владельца от 2026-08-17 (ICP и JTBD): вход пользователя — «фото и характеристики
**или ссылка на текущую карточку**». Это переводит фазу E2 (импорт карточки) из «потом» в MVP.
Контракт импорта не существует, а спроектировать его без ответа на один вопрос нельзя:
**откуда сервис берёт данные карточки** — через официальный API площадки (нужна авторизация
продавца в MVP) или парсингом публичной страницы. Вопрос не только технический: он определяет
юридическую позицию, объём работы на MVP и качество брифа.

Что нужно получить из карточки для брифа: название, характеристики/атрибуты, описание, фото
товара. Способ доступа влияет на три вещи напрямую:

- **юридический риск** — парсинг против санкционированного доступа;
- **качество брифа** — полные атрибуты из API против того, что видно на публичной странице;
- **состав MVP** — попадает ли в первую версию флоу авторизации в кабинете площадки.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы | Лицензия/стоимость |
|---|---|---|---|
| **(а) Официальный API + авторизация продавца** | санкционированный доступ (нет нарушения ToS); структурированные атрибуты → качественный бриф → меньше попыток (северная звезда); стабильный версионированный контракт, не ломается от смены вёрстки; соответствует 289-ФЗ («достоверность карточек» с 01.10.2026) | в MVP нужен флоу авторизации (ввод API-ключа/OAuth) и безопасное хранение креденшелов; каждой площадке — свой клиент; у Ozon/WB разные требования к выдаче ключей | клиенты Ozon MIT (TS-SDK), WB — официальный swagger/OpenAPI, см. Ссылки |
| **(б) Публичная страница (парсинг)** | самый быстрый вход: селлер вставляет ссылку, без настройки ключей; нет хранения чужих креденшелов | нарушение ToS площадок; ломается при смене HTML/антибота; часть атрибутов видна только в кабинете продавца → бриф беднее; юридический риск (блокировка IP, претензии площадки) | готовые парсеры в основном без лицензии или «для канала», см. Ссылки |
| **(в) Гибрид: публичная страница в MVP, API позже** | скорость входа в MVP | откладывает, но не снимает юридическое решение: MVP выходит на ToS-серой зоне; после MVP переделка парсера на API | — |

## Решение

**Рекомендация — вариант (а): официальный API площадки с авторизацией продавца.** Обоснование:

1. **Юридически чисто.** 289-ФЗ вводит с 01.10.2026 проверку достоверности карточек, и наш
   клин — «контроль соответствия ролика реальному товару» — несовместим с добычей данных
   в обход ToS. Парсинг публичной страницы — это нарушение пользовательского соглашения Ozon/WB
   и постоянный риск блокировки.
2. **Структурированные атрибуты.** Официальный API отдаёт полный набор характеристик, часть
   которых на публичной странице не видна. Это прямо снижает число попыток на принятый ролик
   (северная звезда 1,6): бриф предзаполняется реальными данными, а не догадками по фото.
3. **Устойчивость.** Публичный парсинг ломается на каждой смене вёрстки и антибота; API —
   версионированный контракт, который площадки меняют с предупреждением.
4. **Цена авторизации в MVP — осознанная.** Подключение кабинета продавца — одноразовая
   настройка на селлера, а не на ролик, и естественная предпосылка для пакетной обработки
   ассортимента (наш клин № 2). Хранение ключа — отдельная зона безопасности, решаемая
   стандартными средствами (секрет-менеджер, имя переменной окружения в контракте).

Вариант (в) допустим как компромисс скорости, если решено, что флоу авторизации слишком
тормозит MVP: тогда публичная страница — временный путь только для «своей» карточки селлера
(по явной ссылке), а официальный API остаётся целевым путём, зафиксированным этим ADR. Но риск
ToS при этом лежит на нас с первого дня, а не появляется позже.

**Статус решения: за Денисом.** Агент приносит варианты; окончательный выбор фиксируется
изменением статуса этого ADR с «предложено» на «принято» и определяет, попадает ли в MVP
авторизация в кабинете площадки (см. «Блокирующий вопрос» в TEC-26).

## Последствия

**При выборе (а):**

- В контракт импорта закладывается сущность «подключение кабинета» (продавец авторизует
  сервис); хранение ключа — только имя переменной окружения, значение в контракт не попадает.
- Каждой площадке — свой адаптер за единым интерфейсом (как у провайдеров генерации);
  провайдер-специфика не течёт в домен.
- MVP вырастает на флоу авторизации и безопасное хранение креденшелов.

**При выборе (б):**

- Контракт не содержит сущности авторизации, но обязан содержать явную пометку источника
  данных (`public_page`) и TTL хранения (карточка устаревает, площадки меняют разметку).
- Юридический риск остаётся; пересмотр способа доступа после MVP — отдельная задача.

**Общее.** Независимо от способа, хранение импортированной карточки ограничено сроком жизни
(карточка товара — живой объект), а артефакты адресуются ключом S3, не путём в ФС.
