# 0001. Скелет монорепо и границы модулей

**Статус:** принято · **Дата:** 2026-08-17 · **Задача:** сборка скелета до первого эпика

## Контекст

Контур Hermes построен на трёх опорах: Linear — источник задач, git — источник истины, CI — судья. Третья опора отсутствовала: без репозитория и пайплайна «зелёный/красный» не существует, а значит не работают ни детектор топтания у разработчика, ни запрет ревью красного CI, ни счётчик итераций.

Дополнительное ограничение: агент читает только файлы из `scope` задачи. Структура репозитория должна делать такой scope физически возможным — то есть границы модулей обязаны совпадать с границами задач.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Полифрепо (сервис = репозиторий) | независимые релизы | контракты расползаются по репозиториям, кросс-сервисная задача становится нескольким PR, агенту негде взять целостную карту |
| Монорепо с общей сборкой (Nx/Turbo) | кэш, граф задач | лишний слой конфигурации на этапе, где ещё нет ни одного сервиса |
| **Монорепо pnpm workspaces без сборщика** | одна карта, один CI, контракты рядом с кодом, минимум конфигурации | нет инкрементальной сборки; при росте потребуется вернуться к вопросу |

## Решение

Монорепо на pnpm workspaces: `apps/*`, `services/*`, `packages/*`, `contracts/`, `docs/`, `scripts/`, `tests/`.

Сборщик не подключаем: типы проверяются одним `tsc --noEmit` по корневому `tsconfig`, импорты между пакетами разрешаются через `paths` и алиасы vitest. Никаких артефактов сборки на этом этапе не требуется.

Ключевое архитектурное правило скелета — **вся дорогая и рискованная логика вынесена в чистые функции**:

- построение команды ffmpeg (`buildAssemblyArgs`) отделено от её запуска;
- QC — функция над отчётом пробника, а не над файлом;
- решение о расходе — функция над оценкой, лимитами и снимком трат;
- ключ идемпотентности — функция от заказа, сцены, пресета и версии реестра промптов.

## Последствия

**Хорошие.** Тесты не требуют ни ffmpeg, ни сети, ни БД — CI быстрый и не флейкает. Границы модулей совпадают с границами задач, поэтому непересекающийся `scope` достижим. Провайдеры и библиотеки заменяются на краях, не задевая домен.

**Цена.** При росте числа пакетов `tsc` по всему дереву замедлится — тогда потребуется project references или сборщик, и это будет отдельный ADR. Хранилище в памяти в `apps/api` — сознательная времянка; она помечена в коде и в карте репозитория, чтобы не превратиться в постоянную.

**Проверяемо.** `pnpm verify` = линтер + типы + тесты + сверка реестра OSS. В CI дополнительно: линт OpenAPI, проверка обязательных полей в схемах очередей, проверка имени ветки на конвенцию `task/TEC-<id>-<slug>`.
